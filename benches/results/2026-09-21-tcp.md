# TCP stacks over DPDK: faster options, not a general end-to-end win

This comparison ports smoltcp 0.12 to rpkt-dpdk, then substitutes rpkt's TCP
wire parsing/emission while retaining the same connection state machine. It
does **not** present a new, independently implemented TCP state machine.

The rpkt backend substantially reduces option-heavy wire-processing time, but
that improvement must not be presented as an equivalent application-throughput
increase. The live results include near-ties, regressions and loss-sensitive
bulk cases. A consistent, materially faster TCP stack is not established.

## Controlled setup

Measured runtime source: `3bece1a` on `dev/tcp-stack-comparison`, stacked on
PR28. Subsequent changes add runner/documentation/tests and derive the output
label from the stack's actual feature (a feature-unification safeguard); the
documented measured builds already select and label their backends correctly.
Source and executable hashes are in each environment JSON.
All ten recorded source-file hashes per host in both live matrices and the
final profile match `3bece1a`; this was checked against Git, not inferred from
branch names. The later opt-in native-inlining control is a separate build/run.
Both hosts build the same locked dependencies with Rust 1.98 and the
`performance` profile: fat LTO, one codegen unit, no Rust native-target override.
The installed DPDK is 24.11.7 on each host.

- One full-duplex 100-Gb/s link: duanjp `b8:00.1` ↔ tg `17:00.0`.
- duanjp: Xeon Platinum 8580; tg: Xeon Gold 6230. CPU/NUMA placement is fixed
  within each host comparison, not treated as interchangeable across hosts.
- One server/DUT thread, one client thread, one hardware RX/TX queue per host,
  2048 descriptors, burst 64, MTU 1500; duanjp CPU 60, tg CPU 4.
- The DUT alternates between native smoltcp and rpkt. The client on the other
  host is **always the same native smoltcp build**. Both host placements are
  measured; a peer-limited result is not a DUT capacity claim.
- Same Reno controller, immediate ACKs, Nagle disabled, 256-KiB RX/TX socket
  buffers, software checksums, data generation/verification, and polling policy.
  Ethernet/IP/ARP, socket lookup, timers, retransmission and buffering are shared.
- Establish all connections, warm up for two seconds, measure for five seconds
  using the actual recorded interval, then drain. Echo maintains one request
  outstanding per connection; bulk continuously writes to the TCP byte stream.
- Three repetitions with alternating backend order, frozen executables and no
  concurrent builds or live runs. Hosts are not globally isolated: other users'
  jobs are left untouched. Ratios are ratios of medians, not confidence bounds.
- Pause flow control is left unchanged. Temporary duanjp node-2 hugepages are
  restored to zero after each runner invocation. No drivers, host IP addresses,
  link MTUs or network services are changed.

`write` is application write/request size, **not frame size**: TCP may segment
or coalesce it. Throughput is completed echo responses at the client or verified
application bytes at the bulk receiver, not offered traffic or NIC counters.
Full per-run counters, including RX misses, are retained in
[the raw directory](2026-09-21-tcp/).

had no RX misses. All 12 tg bulk trials had RX misses (18,303–901,042 per run,

are delivered TCP goodput under loss, not RFC 2544 zero-loss capacity.

The 1.122x small-write tg median is **not** a robust parsing win: the native
range spans more than 6x. Large-write bulk changes sign with host placement
(+2.4% on tg, −1.2% on duanjp). Echo ratios span 0.995–1.011x. These results
support neither a blanket TCP-stack speedup nor extrapolation of the much
larger option microbenchmark ratios to live TCP throughput.

**Most emission advantages disappear or reverse under native force-inlining.**
Do not credit the original emission ratios solely to rpkt's paired stores or
option templates. Option-heavy **parsing** remains faster in this control
(1.44–3.73x), whereas plain parsing is approximately tied. This supports the
option-parsing implementation as the stronger distinguishing result; it does
not prove that an equally redesigned smoltcp parser could not match it.

## Fair interpretation of the code differences

Both libraries already borrow packet payloads; neither allocates a heap object
to parse a TCP header. The rpkt backend uses:

1. Checked, exact-size fixed-header views. Field bounds are explicit in the
   type, although optimized smoltcp code can also eliminate redundant checks.
2. Borrowed option views instead of the intermediate by-value `TcpOption`
   representation, whose SACK variant contains three decoded ranges. The
   rpkt backend materializes only the final three ranges required by the
   unchanged state machine. Timestamp pairs use a generated combined accessor.
3. Direct fixed-header/option-template emission with generated paired-field
   setters. This avoids the native option-emitter representation layer.
4. An explicit no-options path and inlineable generated iterators. These are
   useful implementation choices, not capabilities exclusive to rpkt. The
   no-options specialization can also be applied to smoltcp.

The compiler change adds `#[inline]` to generated packet/group iterator `next`
methods, including mutable variants, with regenerated outputs and a regression
test. The measurements compare the combined wire implementations; they do not
quantify the independent causal contribution of each item above.

## Shared fixes and exploratory runs

Timestamp-enabled full-sized segments exposed an upstream 0.12 sizing bug:
payload sizing used the 20-byte fixed TCP header even when options were emitted,
allowing packets to exceed MTU. Both variants receive the same option-aware
MSS/MTU correction, consistent with
[RFC 6691 §2](https://www.rfc-editor.org/rfc/rfc6691.html#section-2). Fixing this
only in rpkt would have been an invalid baseline comparison.

Early no-congestion-control pilots stalled under sustained loss on the slower
receiver. Final runs explicitly enable the same Reno controller in both stacks,
and the application rejects a stalled measured receiver. Reno does not make
the small-write bulk workload stable or turn it into a zero-loss benchmark.

Initial profiles showed about 80% of bulk samples inside `tcp_stack::main`
(including inlined application/stack code), and large echo costs in repeated
socket polling. The shared harness
now precomputes the periodic test stream, uses full slice comparisons/copies,
and runs one egress pass after bounded ingress and application work. Verification
is not removed: a separate byte oracle checks wraparound and corruption.
Neither this harness change nor the shared sizing fix is an rpkt advantage.

[Exploratory results and initial profiles](2026-09-21-tcp/exploratory/) are kept
separate from the final matrix. They are not controlled per-optimization
ablations. A tg profiling attempt could not run because that host has no `perf`;
its cleanup restored hugepages, and profiling uses duanjp's installed tool.

## Final CPU profiles

Separate instrumented runs use 997-Hz user-space cycle sampling for three
seconds inside the active window, approximately 3,000 samples each, zero lost
samples. They are not pooled into throughput medians. Percentages below are
fractions of the busy-poll core's sampled cycles, **not per-packet costs**.

| Workload/backend | seq/window polling | TCP ingress | Checksum data | main (includes inlined code) |
| --- | ---: | ---: | ---: | ---: |
| Echo64/16, native | 34.60% | 2.99% | 2.20% | 18.83% |
| Echo64/16, rpkt | 32.07% | 2.73% | 2.87% | 19.18% |
| Bulk1400/16, native | 19.30% | 6.39% | 13.38% | 14.04% |
| Bulk1400/16, rpkt | 20.55% | 5.99% | 13.54% | 13.29% |

`process_tcp` includes TCP parsing **and** socket processing; it is not a pure
parser measurement. Egress parsing/emission can also be inlined into dispatch
functions. The important observation is that the large option-only gains apply
to a small part of a core also doing polling, packet I/O, checksums and memory
operations. The samples do not establish causal savings for individual rpkt
accessors. Full symbol reports are adjacent to
[the profiling run](2026-09-21-tcp/profile-duanjp.jsonl).

Final readback: duanjp node-2 hugepages `0`; all four dedicated link ports
autoneg off, RX pause on, TX pause on, matching their original settings.

## Validation

- Core library/compiler tests and documentation tests pass; compiler diagnostic
  fixtures and regenerated-source checks pass.
- 448 native and 449 rpkt vendored stack tests pass with the documented test
  feature set. The extra test differentially compares random/malformed input,
  every option kind/length and emitted bytes against the retained native code.
- Four application tests pass with each backend: multi-connection echo with
  timestamps, SACK, loss/reordering and full FIN/TIME-WAIT closure; the independent
  stream byte oracle; rejection of corrupted TCP checksums; and backend labels
  under dependency feature unification (also tested without the local feature).
- Differential wire test passes under Miri (one test, about 635 seconds).
- All-feature DPDK examples compile; Clippy completes (existing/upstream warnings
  retained). The TCP reporting unit tests pass.
