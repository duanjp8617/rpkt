# NAT forwarding: generated-code gains and remaining limits

The requested blanket **1.15x end-to-end throughput margin against both pnet
and smoltcp is not established**. The retained generator changes do produce
useful CPU-kernel gains, especially for small packets; they are not a promise
that every memory-working-set or NIC workload becomes 15% faster.

With the fast shared aHash table, all eight 64-byte UDP/TCP combinations
(two hosts, two flow counts) exceed 1.15x versus both competitors in ratios of
median kernel times. Versus smoltcp the margins are 1.161–1.211x; versus pnet,
1.600–2.003x. Larger frames do not consistently clear 1.15x against smoltcp.
For example, tg's 1500-byte/64-flow UDP result is approximately parity (0.995x).
The default SipHash cases also fail the 1.15x smoltcp target.

## What changed

[PR #26](https://github.com/duanjp8617/rpkt/pull/26), commit `694e66b`, adds:

- Opt-in checked disjoint fixed-field/options/payload views. Exact-array
  borrows expose a constant storage bound, without unsafe indexing.
- Packed adjacent integer reads/writes, used for NAT port pairs.
- Generated u32 IPv4 address conversions and shared flag/fragment-word loads.

The new workload also precomputes folded checksum deltas at flow installation,
inlines **all** adapters equally, and offers the same aHash table to every
library. Those shared application improvements must not be attributed solely
to rpkt. The `rpkt_cursor` comparison uses the **new** library with the old
nested-cursor API, not an old-compiler binary. No controlled old-compiler/new-
compiler throughput percentage is claimed here.

A generated flattened Ethernet/IP/transport prefix prototype was tested and
removed: it did not consistently outperform per-protocol views. No unchecked
parsing, payload-specific skipped validation or slower competitor checksum
algorithm was retained.

## CPU method and provenance

See [the equivalent-work contract](../README.md#established-flow-nat).
There are 1,152 estimates: two hosts × two hash policies × four library-order
rotations × 18 workloads × four adapters. Every mean point estimate and 95%
bootstrap interval, plus source hashes and environment metadata, is in
[the machine-readable results](2026-09-18-nat.json).
The table below reports the median of four mean point estimates, in ns/packet;
ratios are competitor time divided by rpkt time, **not confidence bounds**.
No case or outlier run was discarded.

- Rust/Cargo 1.98.0, LLVM 22.1.8; locked pnet 0.35.0, smoltcp 0.12.0,
  aHash 0.8.12 and Criterion 0.5.1.
- Portable x86-64, no RUSTFLAGS; bench profile fat LTO and one codegen unit.
- tg: Xeon Gold 6230, CPU 2, NUMA 0, SMT sibling 82; schedutil with reported
  min/max 2101000 kHz; Linux 5.15.0-185.
- duanjp: Xeon Platinum 8580, CPU 60, NUMA 2, SMT sibling 180; powersave with
  reported min/max 800000/4000000 kHz; Linux 6.17.0-35.
- Affinity was pinned, not exclusive CPU reservation. Background services
  remained running. Temperature, continuous sibling utilization and turbo
  residency were not controlled. Small differences are not universal wins.
- 30 samples, 200 ms warmup, 500 ms nominal measurement, 1000 bootstrap
  resamples. Criterion extends collection when needed for large batches.
- Input reset/allocation is outside timing, but input traversal, packet
  parsing, lookup, rewriting and consumption are included. These are
  established-flow kernels, not a complete NAT gateway or NIC packets/s.
- Table layouts use fixed laboratory seeds. Production deployments should
  choose randomized keyed hashing and test their own traffic distribution.
