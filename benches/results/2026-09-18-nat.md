# NAT forwarding: generated-code gains and remaining limits

The requested blanket **1.15x end-to-end throughput margin against both pnet
and smoltcp is not established**. The retained generator changes do produce
useful CPU-kernel gains, especially for small packets; they are not a promise
that every memory-working-set or NIC workload becomes 15% faster.

With the fast shared aHash table, all eight 64-byte UDP/TCP combinations
(two hosts, two flow counts) exceed 1.15x versus both competitors in ratios of
median kernel times. Versus smoltcp the margins are 1.161–1.211x; versus pnet,
1.600–2.003x. Larger frames do not consistently clear 1.15x against smoltcp.
For example, tg's 1500-byte/64-flow UDP result is approximately parity (0.995x).
The default SipHash cases also fail the 1.15x smoltcp target.

## What changed

[PR #26](https://github.com/duanjp8617/rpkt/pull/26), commit `694e66b`, adds:

- Opt-in checked disjoint fixed-field/options/payload views. Exact-array
  borrows expose a constant storage bound, without unsafe indexing.
- Packed adjacent integer reads/writes, used for NAT port pairs.
- Generated u32 IPv4 address conversions and shared flag/fragment-word loads.

The new workload also precomputes folded checksum deltas at flow installation,
inlines **all** adapters equally, and offers the same aHash table to every
library. Those shared application improvements must not be attributed solely
to rpkt. The `rpkt_cursor` comparison uses the **new** library with the old
nested-cursor API, not an old-compiler binary. No controlled old-compiler/new-
compiler throughput percentage is claimed here.

A generated flattened Ethernet/IP/transport prefix prototype was tested and
removed: it did not consistently outperform per-protocol views. No unchecked
parsing, payload-specific skipped validation or slower competitor checksum
algorithm was retained.

## CPU method and provenance

See [the equivalent-work contract](../README.md#established-flow-nat).
There are 1,152 estimates: two hosts × two hash policies × four library-order
rotations × 18 workloads × four adapters. Every mean point estimate and 95%
bootstrap interval, plus source hashes and environment metadata, is in
[the machine-readable results](2026-09-18-nat.json).
The table below reports the median of four mean point estimates, in ns/packet;
ratios are competitor time divided by rpkt time, **not confidence bounds**.
No case or outlier run was discarded.

- Rust/Cargo 1.98.0, LLVM 22.1.8; locked pnet 0.35.0, smoltcp 0.12.0,
  aHash 0.8.12 and Criterion 0.5.1.
- Portable x86-64, no RUSTFLAGS; bench profile fat LTO and one codegen unit.
- tg: Xeon Gold 6230, CPU 2, NUMA 0, SMT sibling 82; schedutil with reported
  min/max 2101000 kHz; Linux 5.15.0-185.
- duanjp: Xeon Platinum 8580, CPU 60, NUMA 2, SMT sibling 180; powersave with
  reported min/max 800000/4000000 kHz; Linux 6.17.0-35.
- Affinity was pinned, not exclusive CPU reservation. Background services
  remained running. Temperature, continuous sibling utilization and turbo
  residency were not controlled. Small differences are not universal wins.
- 30 samples, 200 ms warmup, 500 ms nominal measurement, 1000 bootstrap
  resamples. Criterion extends collection when needed for large batches.
- Input reset/allocation is outside timing, but input traversal, packet
  parsing, lookup, rewriting and consumption are included. These are
  established-flow kernels, not a complete NAT gateway or NIC packets/s.
- Table layouts use fixed laboratory seeds. Production deployments should
  choose randomized keyed hashing and test their own traffic distribution.

## Live method and limits

The live workload uses the same aHash NAT adapters, compiled with the explicit
`performance` profile (fat LTO, one codegen unit) against DPDK 24.11.7 on both
hosts. The code hashes in the CPU artifact match the retained NAT kernel and
generated packet sources; the subsequent manifest addition only registers
extra correctness tests. Live binary/source hashes and NIC settings are
preserved separately with the live results.

The verified path is tg `17:00.0` → duanjp `b8:00.1` → duanjp `b8:00.0` →
tg `25:00.1`. Both links report 100 Gb/s. The DUT is **one thread on CPU 60,
NUMA 2**, with a local hugepage-backed pool. tg's generator uses CPUs 2/3;
its independent receiver uses CPUs 4/5 and two RSS queues. Generator/receiver
pools use anonymous memory on NUMA 0. The same queue sizes, burst 64, packet
validation, table policy, checksum arithmetic and I/O are used for every DUT.
Sender and sink are allowed more CPU resources; this does not make the DUT
multi-threaded.

Ten cases cover UDP/TCP at 64 bytes with 64/4096 active flows, at 512/1500 bytes
with 4096 flows, mixed UDP/TCP at 64 bytes, and IPv4/TCP options at 128 bytes.
Every case runs three times with DUT implementation order rotated. Each sender
runs for five seconds; the other roles have a 30-second safety bound and stop
one second after accepted traffic ends. There is no process startup time in
the traffic-rate denominator. Returned rates use the final receiver packet
count divided by the sender's measured five-second interval (the larger of the
two generator-worker durations); both receiver queues are drained before final
counters are read. Per-run diagnostic DUT steady rate is the mean of **all
complete interior one-second bins**, excluding the first and final partial
bin. Each displayed result is the median of three run rates. Receiver bins
have per-worker first-arrival origins, so their sum is approximate and is not
used for the headline returned-rate comparisons. All worker
records and counters are retained. No best-bin or best-run selection is used.

Every sink packet gets length/MAC and NIC bad-checksum-status checks. Every
1021st received packet per sink worker gets full byte comparison with the
independent reference plus software checksum validation. Payload correctness
is therefore sampled, not exhaustively checked for every received packet.
The DUT uses NIC checksum validation and a software fallback when status is
unknown. Rejected packets, allocation failures, partial TX, unsent packets,
RX misses and fallback counts are reported, not silently removed.

Pilot-only issues were corrected before this final matrix: off-NUMA allocation,
too-short wall-time bounds, scalar/single-queue receiver limits, and the default
repeating RSS key collapsing correlated synthetic tuples onto one queue.
The final sink uses a deterministic nonperiodic RSS key and the runner verifies
that both receiver workers receive traffic. The kernel adapters were not changed
between DUT implementations.

Pause flow control was enabled on all four interfaces and was **not changed**.
Backpressure can throttle offered traffic, so a sender rate near the DUT rate
does not by itself identify a generator ceiling. These short trials include
loss and are **not** an [RFC 2544 zero-loss throughput determination](https://www.rfc-editor.org/rfc/rfc2544.html#section-26.1).
They do not isolate I/O, memory, pause/backpressure and generator effects into
separate costs. No claim of a universal forwarding-capacity speedup is made.

There is also a physical limit for large frames: 1500 bytes here excludes FCS.
Including four FCS bytes, eight preamble bytes and twelve inter-frame-gap bytes
gives an ideal 100-Gb/s ceiling of `100e9 / (1524 * 8) = 8.202 Mpps`.
The [Ethernet accounting in RFC 2544 Appendix B](https://www.rfc-editor.org/rfc/rfc2544.html#appendix-B)
uses the same preamble/gap model. Once a competitor exceeds 7.132 Mpps on this
link, beating it by 1.15x in delivered packets/s is impossible even at ideal
line rate. This does not explain away the smaller-packet misses; those remain
unmet acceptance cases too.

## Validation and handoff

- Core/compiler tests and doctests, all core features, diagnostic fixtures,
  regeneration drift, bare-metal no_std, and both hash-policy NAT smoke tests
  pass. Extra miss/rejection and omitted-UDP-with-options tests pass.
- Four parts tests pass under Miri; the extended parser fuzz smoke completed
  4,321,239 executions without failure. Existing protocol/TCP-option benchmark
  equivalence checks pass. The NAT options case preserves options; it is not
  a replacement for PR #25's option-extraction workload.
- Both remote hosts compile the native DPDK harness against 24.11.7; local
  DPDK example compilation also passes. Clippy completes with non-blocking
  repository/style warnings.
- On duanjp, `libclang-common-18-dev` was installed to supply the missing Clang
  resource headers; native builds used `LIBCLANG_PATH=/usr/lib/llvm-18/lib`
  and `BINDGEN_EXTRA_CLANG_ARGS=-resource-dir /usr/lib/llvm-18/lib/clang/18`.
- Temporary duanjp node-2 hugepages were restored from 128 to the original
  zero. No `nat-*` hugepage backing files or traffic processes remain.
  MTUs, IP addresses, routes, link pause policy and driver binding were not
  changed. The ordinary hosted hardware-job skip is not evidence of these
  separately recorded native runs.

The compiler improvements and test infrastructure are complete for review.
The broad real-world 1.15x requirement remains unmet; the results above are
the supported outcome, not a claim that the requested performance margin
was achieved everywhere.
