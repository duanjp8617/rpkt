# NAT: unchecked slice access versus checked access

**Result: unchecked access does not improve this NAT workload.** Compared
with the same slice-backed code using checked accessors, small-packet rpkt
medians are about 0.7% lower under default release and 1.1–1.6% lower under
fat LTO. LLVM already eliminates the relevant field bounds checks. Raw access
still leads the competitors modestly on ordinary small packets, but does not
establish a broad 1.15x advantage over both libraries.

## Implementation and experimental control

`pktfmt` now emits direct slice `get_unchecked` / `get_unchecked_mut` calls
for fixed-offset scalar fields, bitfields, byte-slice fields and combined
field pairs. Getters/setters remain safe after checked construction; generated
`parse_unchecked` and structural-length setters are unsafe with documented
obligations. Numeric/value guards and byte-slice source-length checks remain.
Variable-header/payload slices still use checked operations.

There are **no fixed-size array field views** in this implementation. Both
ordinary packets and parts fields access the underlying slices. Parse checks
the contiguous fixed header once. The unsafe `StableBuf` contract preserves
that bound across subsequent shared/mutable access and cloning, without
per-access runtime guards. This is necessary because `bytes::Buf` itself is
safe to implement and does not supply a memory-safety invariant for unchecked
indexing. Pbuf's implementation keeps its exclusive mbuf-chain borrow; headers
crossing a chunk boundary are rejected rather than read across allocations.
See [API migration and safety details](../../rpkt/RAW_ACCESS.md).

Runtime snapshot `fbe5d2a` is extracted into fresh directories on both hosts:
duanjp `/home/duanjp/rpkt-nat-raw-20260922` and tg
`/root/rpkt-nat-raw-20260922`. Another duanjp extraction at
`/home/duanjp/rpkt-nat-checked-20260922` is the controlled checked-access
ablation. Before transformation, 65 runtime inputs in all three extractions
match Git SHA-256 values. The checked control changes only the 16 generated
files: `.get_unchecked[_mut](constant)` becomes `.get[_mut](constant).unwrap()`;
an attribute suppresses now-unused unsafe-block warnings. All 16 transformed
file hashes match an independent reconstruction of that transformation.

This control keeps the **same slice-backed representation and NAT adapter**.
Comparing only with the prior array-backed build would conflate bounds-check
removal with the representation/API migration. The present source also includes
the previously committed short-UDP fallback fix and rejection diagnostics;
it is not the exact `725d45b` runtime used in the prior report.

## Build and live method

- Rust 1.98.0, LLVM 22.1.8, locked dependencies, DPDK 24.11.7.
- Default release: `opt-level=3`, `lto=false`, 16 codegen units. Fat-LTO
  `performance`: `lto="fat"`, one codegen unit. No native-target Rust flags.
  This compares complete profiles, not an LTO-only intervention.
- One frozen DUT binary per profile/accessor variant. Raw rpkt, libpnet and
  smoltcp use the raw binary; `rpkt-checked` uses the checked binary's rpkt
  mode. All other runtime inputs are the same.
- All traffic generation/sinking uses the previous frozen fat-LTO tg binary,
  SHA-256 `da96d0ff68df6f4a22f4a34c2c7e21e22db9871eeeafe1111ccc24a7f6950579`.
  Its source remains `/root/rpkt-nat-release-20260922`.
- Same two 100-Gb/s links, one DUT thread on CPU 60/NUMA 2, two queues,
  vector RX and burst 64; tg generation CPUs 0–3, sink CPUs 4–7. MTU 1500.
  Same fixed-seed aHash table, validation, checksum handling and prefetching
  for every library. TCP option contents are not decoded.
- Four modes interleaved per workload, with order rotated between three
  repetitions. Five workloads per profile: UDP/TCP at 64 and 1500 bytes,
  plus IPv4/TCP options at 128 bytes; all have 4096 flows.
- Accepted returned packets divided by actual generator duration (about
  five seconds), including receiver drain. Not best-bin throughput and not
  zero-loss capacity. Other users' jobs are not stopped; host-wide noise and
  sink loss remain possible. Three repetitions are not a confidence interval.
- Pause temporarily disabled on the same four dedicated ports under prior
  user approval, identically for all modes. Each invocation restores/verifies
  original pause states and node-2 hugepages. No concurrent builds/live jobs.
- Separate active-window profiles do not enter throughput medians. Whole-
  process `perf stat` counters are not active cycles per packet.

Raw access does not improve default-release NAT throughput in this experiment.
Its small-packet medians are about 0.7% below checked access, with overlapping
run ranges; options differ by about 0.1%. These small differences do not
support a stable gain or a strong regression claim from three repetitions.
The 1500-byte cases are near the physical-link ceiling and are not sensitive
tests of parsing capacity. The options result must not substitute for ordinary
UDP/TCP: it exercises a general-parser fallback, not TCP-option decoding.

Across these 60 trials: 12,290,013,440 generator TX, 6,275,121,816 DUT accepted,
6,273,275,448 sink accepted, and 6,144,124 full sink samples. There were 70 sink
rejections before output sampling, 45,171 DUT unsent packets, 2,513,006,533 DUT
RX misses and 130,846 sink RX misses. Allocation/TX-error counters were zero.
Hardware misses do not fully reconcile the offered/received difference; zero
failed output samples is not exhaustive verification of every packet.

The raw/checked small-packet and options ranges do not overlap in these three
fat-LTO repetitions: raw is slower by about 1.6% UDP, 1.1% TCP and 1.9% in the
options fallback. This is a measured regression for these frozen builds, not
proof that unchecked indexing is inherently slower on every compiler or CPU.
Code layout, address formation and store scheduling also change; the experiment
does not isolate each of those mechanisms. Large packets mostly tie near
the link ceiling.

Across these trials: 12,325,361,664 generator TX, 6,428,622,943 DUT accepted,
6,427,079,190 sink accepted, and 6,294,768 full sink samples; zero bad-output
or bad-checksum counts. There were 93 pre-sampling sink rejections, 58,210 DUT
unsent packets, 2,300,327,585 DUT RX misses and 135,444 sink RX misses.
Allocation/TX-error counters were zero; the generator reported 1,216 unsent
packets. The fixed older traffic binary does not record rejected frame
contents, so neither matrix's sink rejections are retrospectively classified.

## Compiler evidence

Disassembly of the frozen DUT binaries gives:

| Function | Profile | Raw bytes | Checked bytes | Raw non-padding instructions | Checked non-padding instructions |
| --- | --- | ---: | ---: | ---: | ---: |
| rpkt forwarding loop | Default release | 7183 | 7183 | 1398 | 1398 |
| rpkt general NAT | Default release | 538 | 538 | 149 | 149 |
| rpkt forwarding loop | Fat LTO | 9717 | 9749 | 1861 | 1862 |
| rpkt general NAT | Fat LTO | 538 | 538 | 149 | 149 |

Under default release, the normalized forwarding-loop difference is only
Ethernet destination store scheduling. The general parser differs only in
Ethernet source/destination store scheduling, under both profiles. Thus the
checked control does not retain extra field-bounds branches in these functions:
LLVM can already eliminate them using the checked parse/split invariants.

Fat LTO additionally changes address generation and register allocation:
raw computes the packet base once and uses base-plus-displacement field
operands; checked retains mbuf data offset as a separate index in many field
loads/stores and computes the combined base for its fallback. This is a
code-generation difference, not evidence of a removed runtime bounds branch.
Instruction scheduling/layout changes can affect timing independently of the
source-level presence of `unsafe`.

`codegen-release.txt` and `codegen-performance.txt` retain reproducible diffs.
The comparison normalizes relocation displacements and padding, retains local
branch destinations as instruction indices, but ignores RIP-relative data/call
targets. It compares instruction shapes, not formal semantic equivalence.
The forwarding loop includes hashing, checksums, counters and I/O integration;
it must not be presented as parser-only cost.

## Active-window CPU profiles

All 24 separate instrumented trials completed: three CPU-sensitive workloads,
four modes and two profiles. Each uses `cycles:P` at 999 Hz, excluding the
first and last 0.25 seconds of the offered-traffic window. Reports contain
about 4,000 samples each, zero lost samples, and zero DUT/sink bad-checksum or
bad-output counts. These are single diagnostic runs, not repeated estimates
of statistically significant sub-percent differences.

Self sample percentages in the forwarding-loop symbol:

| Profile | Pattern | Raw rpkt | Checked rpkt | libpnet | smoltcp |
| --- | --- | ---: | ---: | ---: | ---: |
| Default release | UDP 64 | 54.03% | 54.14% | 54.57% | 54.40% |
| Default release | TCP 64 | 54.82% | 53.59% | 54.18% | 56.46% |
| Default release | Options 128 | 19.13% | 18.35% | 12.40% | 18.44% |
| Fat LTO | UDP 64 | 53.75% | 54.65% | 54.88% | 57.81% |
| Fat LTO | TCP 64 | 52.60% | 53.25% | 53.76% | 55.84% |
| Fat LTO | Options 128 | 18.31% | 18.51% | 12.54% | 18.06% |

For ordinary UDP/TCP, parsing/accessors are predominantly inlined into this
loop together with NAT lookup, checksum updates and counters. Driver RX/TX
and completion symbols (`mlx5_*` and `rxq_cq_*`) account for another 37–43%.
Neither category is parser-only time, and sample percentages from different
throughput runs must not be read as equal amounts of work per packet.

The options workloads take the general fallback. Out-of-line protocol helpers
provide a more specific distinction here:

- libpnet field getter/setter symbols account for 22.05% of default-release
  and 19.24% of fat-LTO samples. rpkt has no corresponding out-of-line accessor
  samples in either the raw or checked build. This supports an accessor
  inlining/code-generation advantage in this fallback, **not an advantage
  newly obtained by making access unsafe**.
- smoltcp's default-release fallback spends 6.55% in IPv4 `payload_mut`,
  address getters and address conversion. Under fat LTO only `payload_mut`
  remains separately visible, at 4.38%. The ordinary UDP/TCP default-release
  paths also show 1.85%/1.67% in `AddressExt::from_bytes`; these separate helper
  samples disappear with fat LTO. Disappearance indicates changed inlining,
  not elimination of all underlying work.
- rpkt's general NAT function has 23.35%/24.67% self samples for default/fat,
  versus checked rpkt's 24.11%/23.81%. Hash-table lookup is a separate symbol
  (about 15–16% for rpkt), not a protocol parsing benefit. These profiles do
  not show a consistent raw-access improvement.

Thus the defensible parsing/accessor distinction is mostly the generated
accessors' integration into the caller and the fallback's header/payload
access organization. This experiment does not establish that unchecked
indexing itself is faster than checked indexing, and cannot establish any
TCP-option-decoder advantage because it never decodes the options.

  regression test passes and regeneration leaves all runtime outputs identical
  to the measured `fbe5d2a` snapshot.
- After all 144 live trials, independent readback confirms all four ports
  restored to autonegotiation off / RX pause on / TX pause on, node-2 hugepages
  restored to zero, no NAT processes left on either host, and all five frozen
  binary hashes unchanged. See `final-restoration.json`.

Recommendation: do not merge this as a demonstrated NAT speedup. It implements
the requested unchecked-access API, but adds unsafe contracts and an API
migration without a measured forwarding benefit. The controlled negative
result is useful evidence for deciding whether that tradeoff is worthwhile.

## Reproduction

Extract `git archive fbe5d2a` into the isolated source directories. Run the
current `dev/checked_accessor_ablation.sh` only in the checked extraction;
the current script uses standard grep/find because duanjp has no `rg`.
Set each host's DPDK `PKG_CONFIG_PATH`. Build raw and checked DUTs with
`dev/build_nat_release.sh release 64-67` and `performance 64-67`.
The helper refuses to overwrite frozen binaries.

Run `dev/nat_lab.py` with the selected raw `--dut-binary`, checked
`--baseline-binary`, fixed tg `--traffic-binary`, corresponding source paths,
`--repeats 3 --vector-rx --sink-workers 4 --gen-workers 4 --disable-pause
--dut-queues 2 --cases udp:64:4096 tcp:64:4096 udp:1500:4096
tcp:1500:4096 tcpopts:128:4096`. Use fresh output files. For profiles use
`--perf --repeats 1` and only the two 64-byte cases plus `tcpopts:128:4096`.
Run all invocations sequentially; provide sudo credentials via the documented
environment variable, never in command arguments or logs.

Summarize complete matrices using `dev/summarize_nat_ablation.py`. Compare
frozen raw and checked binaries using `dev/compare_nat_codegen.py`.
Raw evidence is in [the artifact directory](2026-09-22-nat-raw/).
